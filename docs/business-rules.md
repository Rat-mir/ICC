# Бизнес-правила ICC

Сценарий: креатор создаёт мейкер, загружает PNG, отправляет заявку; администратор принимает решение. Каталог показывает только approved.

| Операция | Допустимые исходные статусы | Результат |
|---|---|---|
| Создание | — | draft |
| Отправка | draft, revision | pending |
| Одобрение | pending | approved |
| Возврат | pending | revision |
| Отказ | pending | rejected |
| Редактирование опубликованного | approved | draft, сброс старого решения |
| Скрытие администратором | approved | hidden |
| Удаление владельцем | draft, revision | удаление при отсутствии персонажей |

Неверный переход возвращает 409 с message. Статусы перечислены в MakerStatus; правила редактирования/отправки — в методах Enum.

1. Создавать мейкеры могут creator и admin; редактировать — автор либо admin. Политики и middleware проверяются сервером независимо от интерфейса.
2. Активный набор для отправки должен содержать body и face; размеры всех активных PNG должны совпадать. Для каждого файла: настоящий PNG, не более 5 МБ, размер от 16×16 до 2048×2048. Повреждённые и маскирующиеся файлы отклоняются; PNG повторно кодируются через GD.
3. pending и rejected нельзя редактировать или повторно отправлять. При revision замечания видны автору; при approved любые изменения требуют новой проверки.
4. Решение reject/request-revision требует непустую причину, иначе 422. Рассматривать можно только pending.
5. Каждый элемент персонажа принадлежит одному одобренному мейкеру и активен. Минимум один элемент; максимум один на категорию; ID уникальны. Порядок выбора хранится в pivot.layer_order.
6. Нельзя удалить мейкер, используемый персонажами, или элемент, включённый в персонажа: 409. Сохранённые проекты не теряют выбранные слои из-за удаления.
7. UNIQUE(user_id, post_id) обеспечивает один лайк на публикацию. PUT и DELETE идемпотентны.
8. Пользователь работает только со своими персонажами, постами и комментариями. Admin модерирует все объекты. Непубличные PNG защищены той же проверкой доступа, что и мейкер.
9. Регистрация всегда создаёт роль user. Креатора назначает admin. Заблокированному пользователю недоступны вход и защищённые маршруты; блокировка и смена роли отзывают токены.
10. Администратор не может заблокировать себя или изменить себе роль через API.

Изменения мейкера/элементов/статусов и сохранение персонажа выполняются в DB::transaction с lockForUpdate. Ошибка откатывает изменения таблиц, в том числе сброс approved → draft. Для файлов, созданных перед транзакцией, предусмотрено удаление при ошибке. Блокировка строк действует в MySQL/InnoDB; SQLite в тестах проверяет корректность логики и откат, но не доказывает поведение блокировок MySQL при конкуренции.

## Уточнения к исходной модели

Семь основных сущностей из обоих DOCX сохранены. Во вспомогательную asset_character добавлено layer_order, чтобы реализовать изменение порядка слоёв отдельного персонажа (пункты 5–6 ТЗ); это атрибут связи, без дублирования PNG. Статус hidden введён для требования скрытия опубликованного мейкера. Категория мейкера определяется по категориям его активных элементов, без новой основной таблицы. Последнее решение модерации хранится в Maker, история решений не хранится, как указано в КП2.

body/face и запрет двух элементов одной категории — принятые проектные правила совместимости. Их следует согласовать на защите, если преподаватель требует другой шаблон конструктора. В рамках утверждённой модели нет версионирования PNG: правка элемента изменяет его для сохранённых конфигураций; смена файла сохраняет старый физический PNG для предотвращения потери данных, но история связей не ведётся.
